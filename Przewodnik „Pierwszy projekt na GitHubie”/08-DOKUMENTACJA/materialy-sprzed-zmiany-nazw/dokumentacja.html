1. Cel, odbiorca i zakres

Odbiorcą jest osoba przygotowująca pierwsze repozytorium. Częstym problemem są brakujące informacje: nazwa, opis, plik README oraz instrukcje celu, uruchomienia i testów. Aplikacja zamienia te deklaracje w sześć jednoznacznych kontroli i uporządkowany plan następnych czynności.

Użytkownik edytuje formularz manifestu albo importuje JSON. Po kontroli widzi wynik, przyczyny problemów i sposób naprawy. Może poprawić dane, porównać liczbę spełnionych reguł, wygenerować szkielet README i pobrać raport. Zestaw może zawierać do 1000 projektów.

Zakres podstawowy

  • Formularz, wybór rekordu i scenariusz kontrolny.
  • Własne wyszukiwanie liniowe i stabilne sortowanie przez wstawianie.
  • Sześć reguł, procent kompletności i plan poprawek.
  • Liczniki, zapis kroków i porównania na większych danych.
  • Import/eksport wersjonowanego JSON oraz generowanie plików.
  • Walidacja bez częściowego zapisu i automatyczne testy.

Czego program nie robi

Nie loguje się do GitHuba, nie odpytuje zdalnego repozytorium, nie wykonuje kodu i nie ocenia jakości instrukcji. Nie używa płatnych API. Wymagany GitHub służy do przechowywania oddawanej pracy, a nie jako zależność działania asystenta.

Scenariusz użytkownika

Deividas wczytuje przykład MojaGra, widzi 50%, dopisuje instrukcję uruchomienia i ponawia kontrolę. Wynik wynosi 66,7%, problem R5 znika, a porównanie pokazuje wzrost o jedną regułę. Następnie pobiera README, raport i manifest do dalszej pracy.

Maksymalna ocena jest możliwa za pełny zakres podstawowy. Nie dodano opcjonalnych profili reguł Python/JavaScript, logowania ani hostingu.

2. Reguły i model danych

Zestaw ma postać {formatVersion:1, projects:[...]}. Projekt zawiera niezmienne ID, nazwę, opis, listę względnych ścieżek, trzy sekcje README i flagę przygotowania demonstracji. Tablica projektów reprezentuje zbiór rekordów; tablica plików zachowuje kolejność wyszukiwania.

Tożsamość: ID jest niepuste i unikalne, składa się z A–Z, cyfr i łączników. Formularz go nie edytuje; nowy projekt otrzymuje pierwsze wolne PROJEKT-n. Import odtwarza identyfikatory z pliku po pełnej walidacji. Dozwolony jest pusty zestaw.

Ograniczenia: do 1000 projektów i 1000 plików na projekt, tekst do 10000 znaków, ID do 80, ścieżka do 512, JSON do 20 MiB. Ścieżki bez .., prefiksu /, znaków sterujących i składni dysku Windows. Wpisy readme.md i docs/README.md nie spełniają R3.

3. Własne algorytmy i koszty

Wyszukiwanie pierwszego README.md

checked ← 0
dla i od 0 do liczbaPlików−1:
  checked ← checked+1
  jeśli pliki[i] == "README.md": zwróć (i, checked)
zwróć (−1, checked)

Własna funkcja linearSearch jest oddzielona od interfejsu. Przeszukuje listę liniowo i kończy na pierwszym dopasowaniu. Najlepszy przypadek ma O(1), najgorszy O(f), dodatkowa pamięć O(1). Dla pustej listy: indeks −1 i licznik 0.

Sortowanie problemów przez wstawianie

A ← kopia listy problemów; comparisons ← 0
dla i od 1 do długość(A)−1:
  klucz ← A[i]; j ← i−1
  dopóki j ≥ 0:
    comparisons ← comparisons+1
    jeśli porównaj(A[j], klucz) ≤ 0: przerwij
    A[j+1] ← A[j]; j ← j−1
  A[j+1] ← klucz
zwróć A, comparisons

Komparator najpierw porównuje ważność (błąd=0, ostrzeżenie=1), a następnie numer reguły. Elementy przesuwamy tylko przy wyniku dodatnim, więc remisy zachowują kolejność: sortowanie jest stabilne. Tablica wejściowa pozostaje niezmieniona.

Najlepszy czas O(k), najgorszy O(k²), kopia danych O(k). Licznik mierzy wywołania komparatora, a nie wszystkie instrukcje pętli. Ślad kroków kosztuje dodatkowo O(k²) znaków; włączamy go tylko dla najwyżej sześciu problemów, nie dla benchmarku 1000 rekordów.

Kontrola najpierw waliduje manifest, przegląda pliki i wszystkie sześć reguł, potem sortuje problemy. Dla pojedynczego projektu łączny koszt to O(f+r+k²), nie licząc długości przetwarzanych tekstów. Biblioteczne sortowanie występuje jedynie w niezależnym wzorcu porównań.

4. Technologie i uruchomienie

Aplikacja używa HTML5, CSS i zwykłego JavaScriptu. Nie ma zależności sieciowych, bundlera ani frameworka. Obrazy są lokalne. Ten sam rdzeń jest udostępniony jako RepoCore w przeglądarce i CommonJS w Node.js, co pozwala testować dokładnie funkcje używane przez stronę.

Uruchomienie z czystej kopii

  1. Rozpakować cały projekt, nie sam index.html.
  2. Otworzyć index.html w przeglądarce. Zachować katalogi src i assets.
  3. Opcjonalnie: Node.js 20+ i polecenie npm start; wejść na http://127.0.0.1:8080. Serwer nasłuchuje wyłącznie lokalnie.
  4. Nie trzeba wykonywać npm install.

Testy jednym poleceniem

npm test
npm run benchmark

Pierwsze polecenie uruchamia wbudowany runner node:test i asercje node:assert/strict. Drugie wykonuje deterministyczne pomiary i zapisuje docs/wyniki-porownan.json. Aplikacja w przeglądarce także udostępnia uruchamianie porównań.

Narzędzia przygotowania i weryfikacji

Testy interfejsu wykonano w Chromium przez Playwright, niezależnie od wymaganych testów rdzenia. Narzędzie to nie jest potrzebne do działania ani do npm test. Dokumentację wyeksportowano do PDF z lokalnego HTML, a prezentację przygotowano przez Marp. W paczce pozostają edytowalne źródła materiałów.

Sprawdzona platforma i ograniczenia

Weryfikacja automatyczna: Node.js 24 i Chromium w środowisku Linux, widok 1440 px oraz 375 px. Sprawdzono również uruchomienie przez file:// bez serwera. Nie deklarujemy testów na każdej przeglądarce ani na komputerze prowadzącego. Przed obroną należy sprawdzić docelowy komputer i pobieranie plików.

Odświeżenie strony resetuje dane. Zapis do JSON jest świadomą czynnością użytkownika; program nie wysyła danych do sieci i nie udaje trwałego zapisu.

Droga danych

Formularz / plik JSON
  → szkic / kandydat
  → pełna walidacja
  → (przy imporcie) potwierdzenie użytkownika
  → jednorazowe zastąpienie stanu
  → kontrola i odświeżenie widoku

Stan zawiera zestaw projektów i aktywne ID. Formularz jest osobnym szkicem. Nieprawidłowa operacja nie zapisuje części projektu: candidate powstaje przed przypisaniem state. Walidator buduje świeży obiekt i nie modyfikuje wejścia. Import uszkodzonego pliku lub anulowanie potwierdzenia pozostawia bieżące zatwierdzone dane.

Aktualność i porównanie

Po wpisaniu danych dirty=true, a interfejs jawnie mówi, że wynik jest poprzedni. Kliknięcie Sprawdź zatwierdza prawidłowy schemat, przenosi bieżącą kontrolę do previous i wylicza current. Zmiana rekordu resetuje historię porównania: nie porównujemy dwóch różnych projektów.

Bezpieczne wyświetlanie i eksport

Elementy tworzymy przez createElement i textContent. Tekst przypominający HTML nie jest wykonywany. README pobieramy jako Markdown, raport i zestaw jako JSON przez Blob. Nie pobieramy haseł ani tokenów. Rozwijane sekcje obsługuje przeglądarka (details/summary), bez osobnej logiki JavaScript.

6. Obsługa i przykład kontrolny

Wczytany przykład ma nazwę MojaGra, pusty opis, dwa pliki index.html i README.md, cel Gra edukacyjna oraz puste uruchomienie i testy. Spełnione są R1, R3 i R4. Kolory ważności zawsze uzupełniają podpisy.

Pierwsza kontrola nie ma poprzednika (—). Po uzupełnieniu uruchomienia i kliknięciu Sprawdź spełnione są R1, R3, R4, R5: 4/6 = 66,7%. Porównanie pokazuje przyrost o jedną regułę, bez dublowania komunikatów.

Wyszukiwanie odwiedza index.html (brak trafienia), potem README.md (trafienie): checked=2. Sortowanie rozpoczyna od R2,R5,R6. Wstawienie R5 daje R5,R2,R6, a R6 pozostaje za R2. Dwa wywołania komparatora odpowiadają dwóm pokazanym krokom.

Eksport szkieletu README nie udaje, że braki zostały naprawione: puste sekcje otrzymują widoczne znaczniki do uzupełnienia. Pełny zestaw danych zapisuje oddzielny eksport JSON.

7. Porównania i interpretacja

Deterministyczny generator tworzy rekordy A-0…A-(n−1), o jednakowej ważności i kolejnych unikalnych numerach. Badamy tę samą implementację i komparator co w aplikacji. Nie tworzymy sztucznie 1000 reguł kontroli: to osobny eksperyment algorytmiczny.

nKolejność wejściaPorównania kluczyZgodność z wzorcem
10uporządkowane9Tak
10odwrócone45Tak
100uporządkowane99Tak
100odwrócone4950Tak
1000uporządkowane999Tak
1000odwrócone499500Tak

Wzorzec to kopia wejścia sortowana niezależnie metodą standardową. Porównujemy kolejność identyfikatorów. W testach uwzględniono również remisy i stabilność. Pomiar nie używa zegara, więc nie zależy od szybkości procesora i nie udaje benchmarku czasu.

Skąd różnica?

Na danych uporządkowanych każda z n−1 iteracji wykonuje jedno porównanie i kończy przesuwanie: n−1. Na odwróconych każdy nowy element przechodzi przez cały uporządkowany prefiks: 1+2+…+(n−1)=n(n−1)/2. Dla n=1000 daje to 999 wobec 499500 porównań. To ilustruje różnicę między O(n) a O(n²).

Szukamy pierwszego dopasowania. Indeks w kodzie zaczyna się od 0, pozycja w interfejsie od 1. Brak trafienia wymaga obejrzenia wszystkich rekordów, tak samo jak trafienie na ostatnim. Dla pustej listy licznik wynosi 0, nie występuje dzielenie przez długość listy.

Wyniki rzeczywiste: powyższe liczby pochodzą z npm run benchmark. Surowe dane są w docs/wyniki-porownan.json. Przy zmianie algorytmu należy ponowić pomiar i zaktualizować materiały, zamiast zachowywać stare wyniki.

9. Wnioski, ograniczenia i źródła

Aplikacja pokazuje związek struktur danych, wyszukiwania, warunków i własnego sortowania z konkretnym problemem użytkownika. Ważność ma pierwszeństwo przed numerem reguły; licznik musi wynikać z faktycznej pętli, a nie ze wzoru wpisanego do widoku. Duże dane uwidaczniają koszt odwróconego wejścia.

Ograniczenia i rozwój

Niepuste treści mogą być nieprawdziwe lub niewystarczające: 100% nie dowodzi działania kodu, dostępności GitHuba ani jakości testów. Nie ma trwałego zapisu po odświeżeniu, należy eksportować JSON. Testowano Chromium, nie wszystkie środowiska. Profil reguł Python/JavaScript jest możliwym rozszerzeniem, ale nie został dodany, aby zachować prosty zakres podstawowy.

Wkład autora i wsparcie AI

Deividas Dirma wybrał minimalistyczny interfejs, tytuł, położenie logo uczelni i ikony kota. OpenAI Codex w OpenClaw pomógł przeanalizować zadanie, przygotować kod, testy i materiały. Narzędzie generowania obrazów służyło wyłącznie koncepcji; ilustracje dokumentacji są zrzutami uruchomionej aplikacji.

Nie przypisujemy autorowi niewykonanych samodzielnych zmian ani opanowania kodu. Przed obroną powinien sam przejść kod i przykłady, wprowadzić i opisać własne zmiany oraz umieć zmienić dane lub regułę. Wyniki testów dokumentują wykonaną weryfikację, nie zastępują tej pracy.
